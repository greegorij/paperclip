## Evidence

The isolated production pilot reached the managed `jarvis-vault` gateway and
successfully read the Jarvis Boot Manifest. The MCP result produced a JSONL
record split into output chunks of roughly 64 KiB. While Paperclip paused the
child stdout stream until asynchronous log persistence completed, Codex
panicked while printing the result:

`failed printing to stdout: Resource temporarily unavailable (os error 11)`

The run then ended as `codex_harness_crash`. No child issue was created. The
scheduled retry was cancelled before it started, both pilot agents were paused,
all temporarily changed run caps and assignments were restored, and Paperclip
remained healthy.

## Root cause

`runProcess` pauses `child.stdout` and `child.stderr` for every received chunk,
then resumes the stream only after the shared asynchronous `onLog` chain
finishes. This transfers database/logging latency into the CLI's stdout pipe.
Codex treats `EAGAIN` from that pipe as a fatal stdout error instead of waiting,
so a large MCP tool result can crash an otherwise successful turn.

## Acceptance

- Codex stdout/stderr are drained continuously even when `onLog` is delayed.
- Log writes remain ordered across stdout and stderr.
- Terminal-result detection and capped stdout/stderr tails remain correct.
- A child that writes multiple chunks larger than the pipe buffer completes
  while `onLog` is intentionally delayed.
- Existing timeout, cancellation, sandbox, and terminal-cleanup behavior stays
  unchanged.
- The fix does not introduce an unbounded in-memory log backlog; queued log
  data is bounded or otherwise explicitly controlled.

## Implementation (2026-07-30)

Scoped option (default unchanged for other adapters):

- `runChildProcess` / `runAdapterExecutionTargetProcess` accept
  `onLogBackpressure: "pause" | "queue"` (default `"pause"`) and optional
  `maxQueuedOnLogBytes` (default `DEFAULT_MAX_QUEUED_ON_LOG_BYTES` = `MAX_CAPTURE_BYTES` / 4 MiB).
- `"queue"` keeps draining child pipes while `onLog` runs on the existing shared
  chain (cross-stream order preserved). Streams pause only when queued onLog
  bytes exceed the budget; they resume at ≤ half budget (hysteresis).
- `codex-local` `execute.ts` passes `onLogBackpressure: "queue"` for the Codex
  CLI process lane.
- Captured stdout/stderr tails, terminal-result scan/cleanup, timeout,
  cancellation (`runningProcesses`), and close-time `logChain` flush are
  unchanged.

Files:

- `packages/adapter-utils/src/server-utils.ts`

## Correction pass (2026-07-30) — only pass

Root review ran the focused queue tests: **bound test passed**; **drain/order
test failed** only because it asserted cross-pipe interleaving
(`OUT0 ERR0 OUT1 …`). Received order was `OUT0 OUT1 ERR0 ERR1 OUT2 OUT3 ERR2
ERR3`. Cross-pipe OS delivery order is not guaranteed.

Corrections made (no commit/push; other in-tree edits preserved):

1. **Test** (`server-utils.test.ts` drain/order case): keep child-exit-while-onLog-held
   drain proof; assert exact stdout/stderr reconstruction from onLog payloads;
   assert monotonic per-stream label order via `matchAll` on reconstructed
   streams; assert `onLog` serialization (`maxOnLogInFlight === 1`). Do not
   assert cross-pipe alternation.
2. **Implementation** (`server-utils.ts`): on child `exit` in `"queue"` mode,
   set `childExited`, resume any backlog pause, and refuse further backlog
   pauses so remaining buffered stdio can drain (avoids `close` stall when
   paused at exit). Byte accounting, half-budget hysteresis while alive, and
   close-time `logChain` flush unchanged. Bound-test behavior while the child
   is still writing is unchanged.

Inspected and left as-is (no additional blockers found): queue byte
increment/decrement around the shared chain; pause only when
`queuedOnLogBytes > maxQueuedOnLogBytes`; resume at ≤ half budget; captured
tails still `appendWithCap`; default budget = `MAX_CAPTURE_BYTES`.

## Prevention classification

**Logging backpressure leaked into model runtime.** Runtime output drainage and
durable log persistence need separate bounded flow-control policies. A slow
database must not be able to make a model CLI crash while printing a valid tool
result.

## Production verification (2026-07-30)

`fork-v0.2.14` was deployed from its exact clean tag after a fresh database
backup. The isolated Jarvis pilot produced a 229,983-byte Codex log, completed
successfully, read the Boot Manifest through the managed vault gateway, and
showed no `Resource temporarily unavailable`, harness panic, or `EPIPE`.

The pilot then stopped at a separate issue-reference contract defect before
creating a Badacz child task. That defect is tracked independently as
`T-202607-008`; it does not invalidate the production proof of this ticket.
