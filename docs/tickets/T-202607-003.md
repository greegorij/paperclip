## Symptom

Production profile-switch (`claude_local` → `codex_local`) with:

- `replaceAdapterConfig: true`
- a complete replacement `adapterConfig` (no Claude-only env)

returns HTTP 200 from `PATCH /api/agents/:id`, but a subsequent `GET /api/agents/:id` still contains inherited adapter-agnostic `env.CLAUDE_CONFIG_DIR`.

Exact PATCH→GET verify in fleet profile-switch correctly fails; automatic rollback restores the prior state precisely. Instrumentation showed the only mismatch was the inherited env.

## Reproduction

1. Agent on `claude_local` with `adapterConfig.env.CLAUDE_CONFIG_DIR` set.
2. `PATCH /api/agents/:id` with `adapterType: "codex_local"`, `replaceAdapterConfig: true`, and a full next `adapterConfig` that omits `env`.
3. Observe 200.
4. `GET /api/agents/:id` still has `adapterConfig.env.CLAUDE_CONFIG_DIR`.

## Proven root cause

In `server/src/routes/agents.ts`, the `if (changingAdapterType)` block unconditionally:

1. re-copies omitted `ADAPTER_AGNOSTIC_KEYS` from the existing config, and
2. runs `preserveInstructionsBundleConfig`,

ignoring `replaceAdapterConfig`.

Required semantics:

- adapter type change **and** `replaceAdapterConfig: true` → caller payload is a full replacement after normal server defaults/normalization; do **not** preserve omitted `env` / `cwd` / instruction-bundle keys
- when `replaceAdapterConfig` is not true → keep the existing preserve-on-type-change behavior

## Repair plan

1. Gate the type-change preserve block on `!replaceAdapterConfig`.
2. Add PATCH+GET route regression: replace=true drops stale env on type change.
3. Confirm non-replace type change still preserves adapter-agnostic fields (existing + env coverage).
4. Grep for other copies of the unconditional preserve-on-type-change pattern.

## Resolution

- The adapter-type-change preservation block now runs only when
  `replaceAdapterConfig` is not true.
- Explicit full replacements no longer resurrect omitted `env`, `cwd`, or
  instruction-bundle keys from the previous adapter.
- Ordinary adapter changes without full replacement keep the existing
  preservation behavior.
- The focused route suite passed 11/11 tests, including a real PATCH followed
  by GET for the replacement case and coverage of the legacy preservation case.

## Could it have been avoided?

Yes — a route-level test of `replaceAdapterConfig: true` together with an
adapter type change would have exposed the contradictory preservation behavior
before the profile switch reached production.

## Fix completeness

COMPLETE. The only adapter-type-change preservation block in the route was
updated, the codebase-wide pattern search found no duplicate implementation,
and both replacement and non-replacement behavior are covered.
