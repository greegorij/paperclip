# T-202608-005: Ponowne wejście w blocked ignoruje istniejący unblockDescriptor

## Objaw

Karta była `in_progress`, ale miała już prawidłowy `unblockDescriptor` z
poprzedniego epizodu / sterowania. Agent po negatywnym odbiorze dwukrotnie
`PATCH`-ował `status: "blocked"` **bez** ponownego przesyłania descriptor.
Route zwróciła `422 Entering blocked requires…`. Karta została osierocona w
`in_progress`; continuation recovery mogła ją ponawiać.

## Reprodukcja

1. Karta `in_progress` z istniejącym `unblockDescriptor` (owner/action).
2. Bez unresolved blockerów, pending interaction ani approval.
3. Agent: `PATCH /api/issues/{id}` → `{ "status": "blocked" }` (bez
   `unblockDescriptor` w body).
4. Oczekiwane: `200`. Faktyczne: `422`.

## Przyczyna źródłowa

W `server/src/routes/issues.ts` walidacja wejścia w `blocked` liczyła:

```ts
const descriptor = updateFields.unblockDescriptor ?? null;
```

Operator `??` traktował pominięte pole jak brak descriptor — ignorował
`existing.unblockDescriptor`. Agent, który już wcześniej ustawił descriptor i
tylko ponownie wchodzi w `blocked`, dostaje 422 mimo prawidłowej podstawy w DB.

## Naprawa (lokalnie w repo, bez deployu)

1. **Effective descriptor:** jawne `null` w patchu = brak; pominięte pole =
   użyj `existing.unblockDescriptor`.
2. **Owner checks** wyłącznie dla nowo przesłanego descriptor (`patchDescriptor`)
   — reuse istniejącego board-owned descriptor przez agenta nie wymaga
   ponownego nazwania ownera.
3. Wymóg dla kart bez descriptor (ani patch, ani existing) pozostaje 422.

### Kontrakt wznowienia komentarzem (bez zmian)

Sprawdzono: soft-blocked comment resume robi `update({ status: "todo" })`, a
`issueService.update` przy wyjściu z `blocked` **czyści** `unblockDescriptor`
(`patch.unblockDescriptor = null`). To celowe czyszczenie przy leave-blocked,
nie zachowanie descriptor — nie zmieniano tej ścieżki.

- istniejący descriptor + `status: blocked` bez descriptor → `200`
- agent + istniejący board-owned descriptor (bez resend) → `200` (bez 403 owner)
- jawne `null` + brak innych podstaw → `422`
- brak existing/patch → `422`
- nowy descriptor nadal waliduje ownera (istniejące case’y 403)

Pozostaje weryfikacja produkcyjna: `in_progress` z persystentnym descriptor
+ PATCH `blocked` bez resendu → 200; orphaned continuation nie zostaje.
Status **OPEN** do weryfikacji runtime; lokalnie: **CORRECTED**.

## Czy dało się uniknąć

**TAK — test effective descriptor.** Walidacja traktowała tylko body, mimo że
descriptor jest polem persystentnym i agenci często ponawiają `blocked` bez
resendu. Test „existing + omit → 200” oraz „explicit null → 422” blokują klasę.
