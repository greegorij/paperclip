# T-202608-003: Konfigurator traci dostęp lub sesję Chrome/agent-browser

## Objaw

Na VPS Chrome 151 i `agent-browser` były już zainstalowane, ale agent Konfigurator
uznał je za nieobecne. Zamiast kanonicznego drzewa narzędzi sondował lokalny CDP
przez proxy i wyciągał wniosek „brak przeglądarki” bez dowodu z katalogu instalacji.

Po naprawie wykrywania drugi rzeczywisty przebieg ujawnił kolejną część tej samej
usterki: instrukcja tworzyła nowy `XDG_RUNTIME_DIR` przy każdym osobnym poleceniu
powłoki. Ta sama nazwa sesji `agent-browser` trafiała wtedy do nowego demona, a
agent po otwarciu formularza w kolejnym kroku widział `about:blank`.

## Reprodukcja

1. Na hoście operatora: Chrome pod `/home/ccuser/.agent-browser/browsers` oraz
   `agent-browser` pod `/home/ccuser/.local/agent-tools`.
2. Uruchom zadanie Konfiguratora wymagające UI.
3. Agent pomija kanoniczny `PATH` / discovery `chrome` i sonduje `127.0.0.1`
   przez proxy sandboxu.
4. Zgłasza brak przeglądarki mimo obecnych binariów.

## Przyczyna źródłowa

Protokół w `package/agents/konfigurator-systemu/AGENTS.md` nie wymuszał jednoznacznie:

1. ustawienia `PATH` na `/home/ccuser/.local/agent-tools/bin`,
2. znalezienia pierwszego wykonywalnego `chrome` pod
   `/home/ccuser/.agent-browser/browsers` przez `find … -print -quit`
   (bez zakodowanej wersji, bez `| head`),
3. fail-closed: `$CHROME` niepuste i wykonywalne, z jednoznacznym echo błędu,
4. dowodu `"$CHROME" --version` przed claimem niedostępności,
5. `export AGENT_BROWSER_EXECUTABLE_PATH="$CHROME"` oraz stabilnego, prywatnego
   `XDG_RUNTIME_DIR` i unikalnej nazwy sesji dostarczanych na cały przebieg,
6. omijania proxy dla sond `127.0.0.1` / `localhost` (np. `curl --noproxy`).

Równolegle brakowało `frappe.grzegorzgolas.com` w
`desired/runtime-capabilities.json` (allowlista wyłącznie Konfiguratora), przy
zachowaniu `workos.grzegorzgolas.com`.

## Naprawa (lokalnie w repo, bez deployu)

1. Zaostrzono protokół przeglądarki w
   `ops/fleet/jarvis/package/agents/konfigurator-systemu/AGENTS.md` — kolejność
   kroków, zakaz claimu bez dowodu, `find … -print -quit` (bez `| head`),
   fail-closed na niepusty/wykonywalny `$CHROME` z jednoznacznym echo błędu,
   `export AGENT_BROWSER_EXECUTABLE_PATH="$CHROME"`, `--version`, `noproxy`.
2. Dodano `frappe.grzegorzgolas.com` do
   `ops/fleet/jarvis/desired/runtime-capabilities.json` obok
   `workos.grzegorzgolas.com`.
3. Testy i README floty asertują obie domeny, ścieżki RO oraz trzy wymagania
   protokołu z recenzji (`-print -quit`, fail-closed, `export AGENT_BROWSER_…`).
4. Harness tworzy pod katalogiem przebiegu prywatny katalog wykonawczy trybu
   `0700`, przekazuje go jako `XDG_RUNTIME_DIR` oraz nadaje unikalną
   `AGENT_BROWSER_SESSION`. Wartości są identyczne w osobnych procesach tego
   samego przebiegu i różne między przebiegami.
5. Instrukcja zabrania tworzenia nowego katalogu wykonawczego per polecenie i
   zatrzymuje się bezpiecznie, gdy harness nie dostarczył poprawnych wartości.
6. Dla zdalnego sandboxa i SSH harness nie przekazuje już hostowej ścieżki
   katalogu wykonawczego. Najpierw tworzy prywatny katalog `0700` po stronie
   celu, a dopiero potem przekazuje jego ścieżkę jako `XDG_RUNTIME_DIR`.
   Niepowodzenie tego kroku zatrzymuje uruchomienie przed adapterem i zwraca
   czytelny błąd środowiska.

## Weryfikacja

Lokalnie (worktree, bez commit/push/deploy) — 2026-08-02:

```sh
node --test ops/fleet/jarvis/tests/runtime-capabilities.test.mjs
```

Wynik: **9 passed / 0 failed** (~95 ms), w tym asercje obu domen
(`workos.grzegorzgolas.com`, `frappe.grzegorzgolas.com`), ścieżek RO oraz
protokołu (`PATH`, `find … -print -quit`, brak `| head`, fail-closed
`[ -z "$CHROME" ] || [ ! -x "$CHROME" ]` + `Chrome discovery failed`,
`export AGENT_BROWSER_EXECUTABLE_PATH="$CHROME"`, harnessowego
`XDG_RUNTIME_DIR` i `AGENT_BROWSER_SESSION`,
`--version`, `--noproxy 127.0.0.1,localhost`, bramka „brak przeglądarki”).

Test usługi katalogu przebiegu: **9 passed / 0 failed**. Obejmuje uprawnienia
`0700`, ciągłość wartości w dwóch osobnych procesach tego samego przebiegu,
izolację różnych przebiegów i zastąpienie przypadkowych wartości operatora.
Kontrola typów serwera również zakończyła się powodzeniem.

Pozostaje weryfikacja produkcyjna: po apply floty Konfigurator musi znaleźć
Chrome przez kanoniczny katalog, przejść fail-closed, podać `--version`,
wyeksportować `AGENT_BROWSER_EXECUTABLE_PATH`, omijać proxy na localhost
i nie zgłaszać „brak przeglądarki” bez tego dowodu. Dwa osobne polecenia muszą
ponadto zachować tę samą otwartą kartę i sesję Chrome. Status pozostaje **OPEN**
do tej weryfikacji runtime.

## Czy dało się uniknąć

**TAK — protokół + test.** Fałszywy negatyw wynikał z niedookreślonej procedury
discovery i sondy CDP przez proxy. Jawny protokół z bramką dowodu oraz asercje
ścieżek/domen/instrukcji blokują regresję przed kolejnym pilotem.
