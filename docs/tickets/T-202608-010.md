# T-202608-010 — Control-plane tools fail after a fleet adapter switch

## Symptom

Reflection Coach completed its process runs but could not use Paperclip tools after switching from `codex_local` to `claude_local`. The scheduled issue was consequently left blocked. A fleet audit found the same failure class on most recently run Claude agents using workspace filesystem confinement.

Production audit on 2026-08-13: all 22 Claude agents and all 4 Codex agents use workspace confinement. The latest run of each Claude agent showed 18 failed and 4 connected Paperclip MCP initializations. The four connected cases had optional managed connections, matching the branch condition described below.

## Proven cause

Paperclip currently has two different delivery paths:

1. Codex receives Paperclip-managed MCP gateways from the heartbeat service.
2. Claude depends on an allowlisted `paperclip` stdio server discovered in a local profile.

For Claude, the profile server is merged into the strict run config only when at least one optional runtime MCP connection exists. An agent with zero managed tool connections therefore gets an empty generated config. The CLI can still discover the profile server outside that config, but workspace confinement hides the host-side Paperclip command and source paths. The server is announced and then fails to start.

The August 4 sandbox mount change only mounts profile paths that were already merged into the generated config. It cannot repair the zero-connection case.

## Required repair

- Define the Paperclip control plane as a mandatory runtime capability, separate from optional external tool connections.
- Deliver the same run-scoped, short-lived HTTP MCP gateway contract to every supported local adapter, including Claude and Codex.
- Keep adapter code responsible only for rendering the shared contract into its CLI-specific config.
- Do not depend on a user profile, an installation path, or the presence of another tool connection.
- Preserve workspace and network confinement without broad host mounts.
- Add a matrix covering Claude and Codex, workspace confinement on/off, zero/many optional connections, and adapter switches in both directions.
- Verify representative live agents after deployment, including Reflection Coach.

## Completion evidence required

- Targeted unit and integration tests pass.
- Full typecheck, test suite and build pass.
- A fresh run can list and call Paperclip tools on Claude and Codex with zero optional connections.
- Switching the same test agent Claude → Codex → Claude does not change tool availability.
- No profile-only fallback is required for the mandatory control plane.

## Prevention

The adapter-switch matrix becomes a release regression gate for future fleet model migrations.

## Implemented repair

- The server now exposes the real Paperclip MCP tool set at an agent-authenticated,
  stateless `/api/mcp` endpoint.
- Heartbeat prepends this run-scoped endpoint for adapters whose registered
  capability contract declares both `supportsRuntimeMcp` and
  `supportsLocalAgentJwt`, even when gateway and connection tables are empty and
  when `managedMcpOnly=false`. Registration rejects an invalid capability pair.
- Claude CLI, Codex CLI, their ACP engines and OpenCode render the
  neutral runtime set into their verified native MCP configuration formats.
- Pi, generic process, Grok and Cursor retain their existing
  first-class control channel through explicit `PAPERCLIP_API_URL` and
  `PAPERCLIP_API_KEY`; no MCP renderer is claimed where a native format was not
  verified in this change. Gemini's shared ACP engine uses the runtime MCP
  contract; its CLI fallback remains on the explicit REST channel.
- Tests exercise the real endpoint's `tools/list`, empty-database heartbeat
  delivery, OpenCode rendering, and the existing
  Claude/Codex/ACP renderer contracts.
- Removed two tracked, unreferenced backup artifacts from adapter and heartbeat
  service directories.
