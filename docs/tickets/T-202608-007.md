# T-202608-007: Anulowanie stale queued run po reassign nie budzi nowego ownera

## Objaw

Gdy queued run zostaje anulowany w `evaluateQueuedRunStaleness` /
`cancelQueuedRunForStaleIssue` z `errorCode: issue_assignee_changed`, komunikat
obiecuje, że nowy właściciel „zostanie wybudzony zamiast” starego przebiegu.
W rzeczywistości anulowanie kończy tylko stary run/wake (`cancelled` /
`skipped`) i **nie** tworzy wake dla aktualnego assignee.

Skutek: karta w `todo` / `in_progress` należy do nowego ownera, owner jest
`idle`, zero live runów — praca stoi mimo systemowej obietnicy w komunikacie
anulowania.

## Reprodukcja

1. Agent A ma queued heartbeat run na issue (jeszcze nie `running`).
2. Issue zostaje przepisane na agenta B (np. Senior → Konfigurator), status
   wykonywalny (`todo` / `in_progress`).
3. Heartbeat próbuje claimować queued run A → staleness:
   `issue_assignee_changed`.
4. Stary run: `cancelled`, stary wakeup: `skipped`.
5. Agent B: brak nowego wake/run; karta stoi.

Żywy dowód: queued run starego Seniora anulowany po reassign do Konfiguratora;
nowy owner idle, zero live runów.

## Przyczyna źródłowa

`cancelQueuedRunForStaleIssue` realizowało wyłącznie anulowanie + zwolnienie
`executionRunId` + event lifecycle. Komunikat o wake nowego ownera był
martwym kontraktem — brakowało wywołania `enqueueWakeup` (ani żadnej innej
ścieżki korektowej) wyłącznie dla `issue_assignee_changed`.

Reassignment API może zbudzić nowego assignee w innych ścieżkach, ale gdy
stary run już siedział w kolejce, anulowanie przy claim **nie** uzupełniało
braku wake — stąd osierocona karta.

## Naprawa

W `server/src/services/heartbeat.ts`, po skutecznym anulowaniu stale queued
runu **wyłącznie** dla `issue_assignee_changed`:

1. Bezpieczny odczyt `currentAssigneeAgentId` z `staleness.details`.
2. Walidacja: niepusty UUID, różny od poprzedniego ownera, karta nadal do
   niego należy, status wykonywalny (`todo` / `in_progress` —
   bez terminalnych / `blocked` / `in_review` bez osobnej podstawy).
3. Jedno idempotentne `enqueueWakeup` dla aktualnego ownera z kontekstem
   `issueId`, `wakeReason: issue_assigned`, powodem systemowym
   `stale_queued_run_assignee_changed` oraz kluczem
   `stale_queued_run_assignee_changed:{issueId}:{cancelledRunId}:{newOwnerId}`.
4. Respekt istniejących bram `enqueueWakeup` (pauza, limity, suppression,
   blokery, invokability). Przy stłumieniu — jawny ślad skipped wake / log;
   bez pętli retry. Ponowne wejście z tym samym kluczem nie dubluje.

**Wyścig współbieżny (bloker przed wydaniem):** `cancelQueuedRunForStaleIssue`
nie używa już bezwarunkowego `setRunStatus`. Przejście do `cancelled` idzie
przez `setRunStatusIfQueued` (atomowy `UPDATE … WHERE status = 'queued'` +
publikacja zdarzeń jak w `setRunStatusIfRunning`). Tylko zwycięzca wyścigu
czyści wakeup/lock i wywołuje `maybeEnqueueWake`. Bez migracji / unikalnego
indeksu na wake requests — guarded transition wystarcza jako single-winner
gate.

Testy: `server/src/__tests__/heartbeat-stale-queue-invalidation.test.ts`.

## Weryfikacja

Lokalnie (worktree, bez commit/push/deploy):

```sh
pnpm --filter @paperclipai/server exec tsc --noEmit -p tsconfig.json
pnpm exec vitest run server/src/__tests__/heartbeat-stale-queue-invalidation.test.ts
```

Oczekiwane regresje:

- reassign queued run → stary `cancelled`/`skipped`, nowy owner dokładnie
  jeden wake/run z deterministycznym `idempotencyKey`;
- ponowne `resumeQueuedRuns` nie dubluje;
- równoległe `resumeQueuedRuns` na tym samym reassigned queued runie →
  dokładnie jeden correction wake/run (guarded `queued→cancelled`);
- brak wake przy null assignee / statusach niewykonywalnych
  (`blocked`, `in_review`, `done`, `cancelled`).

Uwaga VPS: test tabelaryczny (5 przypadków) ma jawny timeout `30_000` ms.
Pozytywne ścieżki po asercjach wołają `cancelRun` +
`drainHeartbeatRunsToQuiescence` (`drainActiveRunExecutions`), żeby
correction run nie pisał do DB po truncate w afterEach (FK / Agent not found).

Pozostaje próba produkcyjna: po deployu, reassign z queued runem starego
ownera → nowy owner dostaje wake i karta nie stoi idle. Status biletu
**OPEN** do tej weryfikacji; lokalnie: **CORRECTED**.

## Czy dało się uniknąć

**TAK — kontrakt komunikatu ↔ implementacja + test.** Komunikat anulowania
obiecywał wake, którego kod nigdy nie wykonywał. Test „cancels when assignee
changes” sprawdzał tylko cancel/skip starego runu i nie asertował wake
nowego ownera — regresja produkcyjna była niewidoczna dla suite. Dodatkowo
unguarded `setRunStatus` przy cancelu pozwalałby na zdublowanie wake przy
równoległych claimach (multi-instance / race) — brakowało testu
współbieżności.

## Kompletność naprawy

Werdykt po weryfikacji produkcyjnej. Lokalnie: minimalna korekta w ścieżce
stale-queue + regresje (w tym concurrent cancel); bez obchodzenia bram
`enqueueWakeup`; bez migracji DB.

## Notatki

- Zakres celowo ograniczony do `issue_assignee_changed` (nie do
  `issue_review_participant_changed` ani innych kodów stale).
- Nie dodawano nowej warstwy recovery — reuse `enqueueWakeup`.
- Single-winner: `setRunStatusIfQueued`, nie unikalny indeks na
  `agent_wakeup_requests.idempotency_key`.
