## Evidence

Production: cancelling a sandboxed Codex run closed a proxy socket while a
piped peer was still writing. Node emitted an unhandled `Socket` error with
`code: EPIPE`, which crashed the whole Paperclip process (not just the run).

The allowlist proxy in `startNetworkAllowlistProxy` piped HTTP
request↔upstream and CONNECT client↔upstream with incomplete error/close
symmetry. The TCP bridge helper already tore down pairs on `error`; the Unix
socket proxy path did not.

A first fix applied symmetric `error`+`close` teardown to HTTP as well. That
stopped EPIPE but was incorrect for HTTP: normal IncomingMessage/ClientRequest
`close` is part of a successful lifecycle, so close-based pair teardown could
destroy the upstream (or downstream response) prematurely and break streaming
success paths.

## Root cause

1. One-sided listeners left the opposite stream without an `error` handler →
   uncaught EPIPE on client disconnect mid-stream.
2. Treating HTTP like a bidirectional socket pair (teardown on every `close`)
   over-corrected: successful request completion must not destroy the upstream
   before the full upstream response is delivered.

## Acceptance

- CONNECT proxy piping keeps bounded, symmetric teardown: error or close on
  either socket destroys that pair only (bidirectional tunnel).
- HTTP proxy piping uses abort/error-scoped lifecycle handling:
  - request abort/error or incomplete request close → destroy upstream
  - downstream `close` when `!response.writableEnded` → destroy upstream
    (and upstream response if any)
  - upstream error → proxy error response if headers not sent, else destroy
    response
  - upstreamResponse error → destroy response
  - successful completion must finish the upstream request and allow the full
    upstream response (do not tear down solely because request closed after
    the body was fully received)
- Client disconnect / EPIPE during upstream streaming does not become an
  uncaught process exception and does not crash Paperclip.
- Unrelated errors outside these pairs are not globally swallowed.

## Tests

- `packages/adapter-utils/src/local-process-sandbox.test.ts`
  — disconnects a proxy client while upstream is streaming; asserts no
  `uncaughtException` (EPIPE regression).
  — completes a multi-chunk streaming HTTP proxy response with status 200 and
  full body (success-path lifecycle).

## Correction pass note (2026-07-30)

- Code: HTTP path switched from `bindProxyPairTeardown` to
  `bindHttpProxyLifecycle`; CONNECT retains `bindProxyPairTeardown`.
- The orchestrator ran both focused regressions and package typechecks; all
  passed. Full repository CI also passed before the tagged release was
  deployed.
- Paperclip remained healthy during the subsequent pilot and cancellation
  cleanup. That cleanup cancelled a queued run, so it is not claimed as a
  second live reproduction of the original mid-stream disconnect.

## Prevention classification

- **Incomplete pipe lifecycle** — every `.pipe()` between sockets/streams in
  the sandbox proxy must attach paired teardown appropriate to the hop type
  (socket pair vs HTTP request/response) before first write.
- Keep regression coverage that forces mid-stream client destroy **and** a
  successful multi-chunk proxy completion; unit parsing tests alone cannot
  catch process-level EPIPE or premature close teardown.

Assignment recovery / quarantine UI. This ticket is only the proxy crash path.
